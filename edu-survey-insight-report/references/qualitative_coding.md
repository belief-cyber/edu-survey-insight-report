# 주관식 전수 코딩 절차

## 왜 전수 검토인가
패키지의 주제 코딩은 PROPOSED(탐색적 후보)이고 오류가 많다(예: "수업과 겹쳐 1시 시작이면 좋겠다"가 '긍정 경험'). 키워드 정규식도 후보를 찾을 뿐이다.
보고서의 모든 주제 빈도·인용은 **사람이 읽고 확정한 코드**에서 나와야 한다.

## 절차
1. `qual_prep.py` → `qual_review.md`(대상 교육 → 그 외 교육 순, 교육별 묶음)와 `qual_auto.json`(자동 후보 코드).
2. `qual_review.md`를 **처음부터 끝까지 읽는다**. 분량이 많으면 나눠 읽되 건너뛰지 않는다. 대상 교육 행은 하나도 빠짐없이 판단을 남긴다.
3. 판단을 `overrides.json`에 기록한다.
   ```json
   {"Q-2099-예시교육-01-00013-026": {"add": ["N_SCHEDULE", "N_VENUE"], "remove": ["P_ACCESS"], "note": "다음 수업 때문에 일찍 종료 요청, 식사량"},
    "Q-2099-예시교육-01-00002-027": {"add": [], "remove": ["*"], "note": "일반 인사"}}
   ```
   - `remove: ["*"]` = 자동 코드 전부 제거(일반 인사·내용 없음).
   - 자동 코드가 맞으면 `{"add": [], "remove": [], "note": "확인"}`로 검토 흔적만 남겨도 된다.
4. `qual_finalize.py` → `qual_final.json`, `qual_summary.md`. 없는 ID·코드가 있으면 멈춘다.
5. 같은 데이터 버전이면 overrides.json은 **대상이 달라도 재사용**할 수 있다(코딩은 원문 단위, 대상/그 외 구분만 바뀜). 단, 새 대상 교육의 행은 다시 확인한다.

## 코드 판정 기준 (assets/codebook.json)
- **P_** 긍정 경험 / **N_** 불편·개선 요구 / **D_** 교육 수요·운영 형태 선호.
- 조건문 속 칭찬("~해주시면 도움이 될 것 같다")은 P가 아니라 해당 N/D 코드.
- 속도 때문에 어렵다 → `N_PACE`(N_TOO_HARD 아님). 내용 자체가 어렵다 → `N_TOO_HARD`.
- "이런 교육이 더 있었으면", "또 참여하고 싶다" → `D_CONTINUE`. 특정 주제·도구·대상 요청 → `D_TOPIC`.
- 현장 식사·간식·교육실 → `P_VENUE`/`N_VENUE`. 시간대·온라인·분량이 편리 → `P_ACCESS`.
- 코드북에 없는 반복 주제가 3명 이상 나오면 codebook.json에 코드를 추가하고(label·polarity·desc·pattern) 추가 사실을 보고서 한계에 적는다.

## 인용 규칙
- 큰따옴표 “ ”는 **원문 그대로**일 때만. 생략은 “…”. 맞춤법 오류도 고치지 않는다.
- 제안 문항·아이디어 문구는 「 」 또는 ‘ ’를 쓴다(validate_content.py가 “ ” 안의 문장을 원문과 대조).
- 인용에는 주관식ID(또는 끝 두 마디, 예: 01-00013)를 붙이고 `ev.q`로 근거 버튼을 연결한다.
- 실명이 들어간 원문은 마스킹된 텍스트로만 인용.
